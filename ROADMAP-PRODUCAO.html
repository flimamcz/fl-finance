02

O que “grátis” significa na prática

Planeje as limitações antes que elas virem indisponibilidade ou perda de dados.

⏱Render Free: serviço web pode dormir após 15 minutos sem tráfego; a próxima chamada pode aguardar cerca de um minuto.
💾Disco: o filesystem do serviço Render é efêmero. Não use SQLite, arquivos locais ou uploads como armazenamento permanente.
📦Render Postgres gratuito: não serve como banco permanente; a documentação atual informa expiração após 30 dias. Não é compatível com o MySQL que este app usa.
🧮TiDB Starter MySQL: a documentação informa 5 GiB de armazenamento e 50 milhões de RUs/mês por instância elegível; ao atingir a cota, novas conexões podem ser negadas até o reset/upgrade.
🔁Rotinas: o backend executa liquidação de parcelas por timer. Um serviço gratuito que dorme não executa tarefas de forma contínua; teste o fluxo e não dependa de horário exato.
🛟Backups: exporte e teste a restauração. Não assuma retenção, backup automático ou SLA no free tier.
03

Preparação no repositório

Faça isso antes de conectar serviços públicos ao banco.

Confirme o estado local

Rode frontend e backend localmente, valide login, setup inicial, criação/edição de transação, dívidas, investimentos, importação e exportação.

Confira o ponto de partida

  • Frontend: frontend, comando de build npm run build, saída dist.
  • API: backend, inicia com npm start, escuta PORT e 0.0.0.0.
  • O backend lê variáveis do ambiente e, localmente, o arquivo .env na raiz do repositório.
  • As migrações ficam em backend/src/migrations; o script existente é npm run db:migrate.

Prepare o Git com segurança

Faça push para um repositório privado, se preferir. Verifique que .env, senhas, dumps do banco e chaves JWT não estão commitados. Nunca use variáveis VITE_* para segredos: elas podem ser incorporadas no JavaScript público.

04

Crie o banco e prepare TLS

O código atual usa Sequelize + mysql2; o TiDB exige conexão criptografada.

Crie uma instância MySQL-compatible

No console TiDB Cloud, crie TiDB Cloud Starter em uma região próxima do serviço da API. Salve host, usuário com prefixo da instância, senha e nome do banco. Crie o banco no console, se necessário, e limite o usuário às permissões necessárias.

Habilite TLS no Sequelize

Antes de migrar, ajuste backend/src/config/config.js. Mantenha a verificação de certificado ligada; não use rejectUnauthorized: false.

const config = {
  username: process.env.MYSQL_USER,
  password: process.env.MYSQL_PASSWORD,
  database: process.env.MYSQL_DATABASE,
  host: process.env.MYSQL_HOST,
  dialect: "mysql",
  dialectOptions: {
    ssl: {
      minVersion: "TLSv1.2",
      rejectUnauthorized: true
    }
  }
};

Habilite TLS também no script de migração

Em backend/scripts/db-migrate.js, passe TLS na conexão mysql2 usada para criar/verificar o banco:

const connection = await mysql.createConnection({
  host: process.env.MYSQL_HOST,
  user: process.env.MYSQL_USER,
  password: process.env.MYSQL_PASSWORD,
  ssl: {
    minVersion: "TLSv1.2",
    rejectUnauthorized: true
  }
});

Confirme na tela “Connect” do TiDB o hostname, usuário e os parâmetros atualizados. O usuário normalmente inclui o prefixo de instância; copiar somente “root” pode falhar.

Migre e confira o schema

Faça primeiro um backup/export. Configure temporariamente no seu terminal seguro MYSQL_HOST, MYSQL_USER, MYSQL_PASSWORD e MYSQL_DATABASE da instância de teste; na pasta backend, rode npm.cmd run db:migrate. O script cria o banco caso ainda não exista e aplica as migrations.

Teste todas as migrations neste provedor antes de importar dados reais: compatibilidade de protocolo MySQL não garante compatibilidade idêntica de cada operação SQL. Não rode db:drop contra produção.

Crie o administrador e migre seus dados, se houver

Com schema vazio, use a tela /setup e confirme em /auth/setup-status que a configuração inicial foi concluída. Se já tem dados locais, exporte o backup completo pelo app, teste a restauração numa instância de ensaio e só então importe uma vez no ambiente final, conferindo transações, categorias, dívidas/parcelas e investimentos/movimentos relacionados.

A configuração inicial é um endpoint público de uso único: não compartilhe a URL do app/API antes de criar o administrador inicial. CORS não impede chamadas diretas de scripts ou servidores.
O TiDB documenta TLS obrigatório no Starter. A API e o comando de migração precisam usar TLS; configurar apenas HTTPS no navegador não protege a conexão backend↔banco.
05

Publique a API: Node + Express no Render

Crie um Web Service conectado ao repositório, selecionando como raiz o diretório backend.

Configure build, start e health check

  • Runtime: Node. Root Directory: backend.
  • Build Command: npm install. Start Command: npm start.
  • Health Check Path: /health. O endpoint existente confirma que o processo HTTP responde; não testa a conexão ao banco.
  • Não fixe uma porta em código/plataforma: o servidor usa process.env.PORT e 0.0.0.0.

Cadastre variáveis no painel da API

Use a área Environment do serviço. Valores são placeholders; os reais devem vir do console do banco e ser gerados por você.

Gere o JWT secret localmente com Node: node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))". Copie o resultado diretamente para o secret do Render; não salve em arquivo versionado.

Entenda CORS e HTTPS

O código lê FRONTEND_ORIGINS e compara a origem exata. Quando NODE_ENV=production, não há origem local liberada por padrão. O HTTPS é terminado pelo Render; use somente a URL https://…onrender.com no frontend. Se conectar domínio próprio, cadastre também a nova origem exata no CORS.

  • Não use * como origem em produção.
  • Não coloque caminho (/home) ou barra final no valor da origem.
  • URLs de Preview da Vercel não são automaticamente permitidas; mantenha produção e Preview controlados.
  • Não é necessário habilitar cookies cross-site para a autenticação Bearer deste app.

Faça o primeiro deploy e anote a URL pública

Após deploy bem-sucedido, teste https://SUA-API.onrender.com/health. Copie somente o hostname/URL HTTPS; será usado em VITE_API_URL.

06

Publique o React + Vite na Vercel

É um frontend estático: a URL da API é compilada durante o build.

Crie o projeto Vercel a partir do Git

  • Selecione o repositório e defina Root Directory como frontend.
  • Framework Preset: Vite (ou detecção automática).
  • Build Command: npm run build; Output Directory: dist.
  • Cadastre VITE_API_URL=https://SUA-API.onrender.com no ambiente Production.
VITE_API_URL não é segredo; será público no bundle. Nunca cadastre JWT secret, senha SQL ou credenciais na Vercel.

Configure navegação SPA (React Router)

Este app tem caminhos como /home e /setup. Para abrir ou atualizar uma rota diretamente na Vercel, adicione frontend/vercel.json com fallback para o index da SPA:

{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}

Conecte a origem ao CORS e redeploy

Copie a URL de produção da Vercel e atualize FRONTEND_ORIGINS no Render, sem barra final. Salve, deixe o backend redeployar e faça novo deploy do frontend se alterou VITE_API_URL. Vercel e Render fornecem TLS gerenciado nos seus domínios.

08

Antes de colocar dados reais

HTTPS é necessário, mas não basta para tornar um serviço financeiro pronto para produção.

Troque o ambiente de ensaio por infraestrutura compatível com o risco

Use backend sempre ligado, banco gerenciado com backups automáticos/retidos, restauração point-in-time quando disponível, alertas, cotas e uma política de recuperação testada. Avalie controles contratuais, residência dos dados, disponibilidade, suporte e requisitos legais aplicáveis.

Operação e segredos

  • Use credencial de banco exclusiva para a aplicação; evite usuário root e permissões globais.
  • Ative MFA nas contas de hospedagem/Git; restrinja colaboradores e tokens.
  • Gire credenciais se forem expostas; não envie dados financeiros ou tokens para logs.
  • Monitore falhas de login, erros 5xx, conexões DB e limites de uso; defina alertas de custo.
  • Faça atualizações de dependências e mantenha produção e Preview isolados.

Revise tarefas agendadas e escala

O servidor executa liquidação automática por setInterval. Serviços gratuitos podem pausar; múltiplas réplicas também podem executar a rotina ao mesmo tempo. Antes de escalar, transforme a tarefa em job idempotente/único e use scheduler/worker apropriado.

Não importe backup financeiro pessoal para uma infraestrutura de ensaio sem entender retenção, acesso e exclusão. Use dataset fictício até ter controles e restauração verificados.
